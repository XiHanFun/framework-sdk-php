The PHP implementation of [XiHan Spec](https://github.com/XiHanFun/framework-spec): the primitives layer, manifests, the invocation context, the pipeline, operation contracts and the out-of-process plugin runtime. Semantics, error codes, message keys and wire encoding follow the spec and match the .NET reference implementation ([XiHan.Framework](https://github.com/XiHanFun/XiHan.Framework)), with an API that follows PHP conventions; the spec lives in `spec/` as a submodule, and conformance is verified by the vectors in the spec repository.

## Getting Started

```bash
composer require xihanfun/xihan-framework
```

Requires PHP 8.3+; at runtime it depends only on the PHP core and `ext-json`. The plugin runtime needs optional dependencies as well (listed under `suggest` in `composer.json`, see [Write a Plugin](#write-a-plugin)).

Operations and the pipeline in a PHP application:

```php
use XiHan\Framework\Invocation\Context;
use XiHan\Framework\Operation\{Codec, Contract, Expose, Invoker, Registry, Request, Shape};
use XiHan\Framework\Pipeline\{ClosureMiddleware, PipelineBuilder, Placement};
use XiHan\Framework\Primitives\{BaggageKeys, Error, PipelineStage, Result, Stability};

final readonly class CreateOrder
{
    public function __construct(public int $quantity) {}

    /** Request shape: quantity is a required 32-bit integer */
    public static function shape(): Shape
    {
        return Shape::object(['quantity' => Shape::int32()->required()]);
    }

    /** Creates the request from the checked value */
    public static function create(mixed $value): self
    {
        /** @var array{quantity: int} $value */
        return new self($value['quantity']);
    }
}

final readonly class OrderCreated
{
    public function __construct(public string $id, public int $quantity) {}
}

$registry = new Registry();
$registry->add(
    new Contract('orders.create', Stability::Stable, [Expose::Http], permission: 'orders.write'),
    static function (Context $context, CreateOrder $request): Result {
        if ($request->quantity <= 0) {
            return Result::fail(Error::validation('ORDERS_VALIDATION_001', 'orders.quantity.invalid', ['min' => 1]));
        }

        return Result::ok(new OrderCreated('o-' . $context->correlation(), $request->quantity));
    },
    Codec::typed(CreateOrder::class, CreateOrder::shape(), CreateOrder::create(...), OrderCreated::class),
);

$observe = new ClosureMiddleware('App\Observe', static function (Context $context, \Closure $next): Result {
    $outcome = $next($context);
    // Record logs and metrics here; $outcome->error() is the failure reason

    return $outcome;
});
$invoker = new Invoker($registry, (new PipelineBuilder())->useAt($observe, PipelineStage::Observe, Placement::End, 'app'));

$context = Context::create(timeout: 2.0, baggage: [BaggageKeys::CORRELATION => 'c1']);
$response = $invoker->invoke($context, new Request('orders.create', '{"quantity":2}'));
echo json_encode($response->outcome), ' ', $response->payload; // {"ok":true} {"id":"o-c1","quantity":2}
```

- Operations are registered with `Registry::add`: the contract, the handler, a `Codec` and an optional `Schema`. PHP has no reflection-free typed JSON decoding, so `Codec::typed` takes the request type name, the request shape (`Shape`, rooted at `Shape::object()` or `Shape::mapOf()`), a factory function and the response type name explicitly; when no type is needed, use the default `Codec::json()`, and the request is a `JsonObject` read under the value model.
- Error codes follow `<DOMAIN>_<KIND>_<NNN>` with the domain in uppercase, and text uses message keys; `Error::message()` resolves by locale through the catalog set with `MessageScope::setDefault(new MessageCatalog([...]), 'zh-CN')`, and is "key (arguments)" when there is none.
- `Invoker::invokeTyped($context, $id, $request, $responseType)` runs with the request object directly, without going through JSON.

Manifests and primitives:

```php
use XiHan\Framework\Manifest\Manifest;
use XiHan\Framework\Primitives\{Error, Result};

$manifest = Manifest::readFile(__DIR__ . '/xihan.manifest.json'); // Throws ConfigurationException (KERNEL_CAPABILITY_006) when invalid
echo $manifest->toJson();                                         // Laid out per RFC-0002 "Writing", identical byte for byte in every language

echo Result::fail(Error::literal('ORDERS_CONFLICT_001', 'stale'))->toJson();
// {"ok":false,"error":{"code":"ORDERS_CONFLICT_001","message":"stale"}}
$result = Result::fromJson('{"ok":true,"value":{"id":"o1"}}');   // Result with a value; objects are JsonObject, $result->valueOrThrow()['id']
$done = Result::unitFromJson('{"ok":true}');                       // Result without a value
$found = Result::maybeFromJson('{"ok":true,"value":null}');        // Result whose value type is Maybe; null means no value
```

### Write a Plugin

An out-of-process plugin is a child process started by the host that talks to it over the gRPC protocol `xihan.plugin.v1` (RFC-0017). The dependencies of the plugin runtime are optional; install them when you need them:

```bash
composer require xihanfun/xihan-framework amphp/socket amphp/http google/protobuf
```

When they are missing, `Runtime::serve()` refuses to start: it writes an `error` log line to stderr naming the packages to install and returns a nonzero exit code. The entry script:

```php
use XiHan\Framework\Invocation\Context;
use XiHan\Framework\Operation\{Contract, Registry};
use XiHan\Framework\Plugin\{Options, Runtime};
use XiHan\Framework\Primitives\{JsonObject, Result, Stability};

require __DIR__ . '/vendor/autoload.php';

$registry = new Registry();
$registry->add(
    new Contract('greetings.create', Stability::Experimental),
    static fn (Context $context, JsonObject $request): Result => Result::ok(['text' => 'Hello, ' . $request['name']]),
);

// The host starts the plugin with the plugin directory as the working directory: the handshake sends this manifest as is, and the host compares it field by field with the file in the directory
exit(Runtime::serve(new Options(
    manifest: (string) file_get_contents(getcwd() . '/xihan.manifest.json'),
    registry: $registry,
)));
```

- Manifest (`xihan.manifest.json`): `kind: plugin`, `isolation: out-of-process`, and `primitives` set to the primitives major version this SDK supports, `1`; every operation the plugin serves is listed in `contributes.operations` (plugins serve unary operations only; streaming operations wait for the streaming contract of RFC-0011), and health items in `contributes.health`; to call back the host, declare `capability:kernel.pipeline` (`Host::invoke`) or `capability:messaging.queue` (`Host::publish`) in `permissions`; `contributes.pipeline` must not be written (only Wasm plugins can contribute middleware). When the declarations do not match the manifest, `serve()` refuses to start: it does not listen, writes no handshake line, writes an `error` log line to stderr and returns `Runtime::EXIT_REFUSED` (1).
- Entry: `entry` is an executable relative to the plugin directory. The host passes on only the environment variables listed in `handshake.md` §1, so the launcher writes the absolute paths of PHP and the entry script: on Unix an executable sh script with a shebang (`exec /usr/local/bin/php /srv/greetings/plugin.php "$@"`), on Windows a `.cmd` (`@"C:\php\php.exe" "C:\srv\greetings\plugin.php" %*`).
- Lifecycle hooks (`Hooks`: `configure`, `start`, `stop`, `health`), event subscriptions (`Subscription`, whose handler receives the `Context`, the `Envelope` and the delivery attempt) and the plugin's own message catalogs (`Catalog::fromDirectory()`) are all given in `Options`. Besides the configuration section as is, the `Configuration` passed to the configure hook reads values by key with `string()`, `int()`, `float()` and `bool()` (member names are matched ASCII case-insensitively, and the leaves written by the .NET host are all strings). Inside a handler, `Host::of($context)` returns the host callback client.
- Verify with the black-box runner of the spec repository (needs Go): in `spec/conformance`, run `go run ./cmd/xihan-conformance plugin --dir <plugin directory> --json`, with `--config`, `--sample <operation ID>=<request JSON>` and `--exclude <operation ID>` for the configuration section, request samples and operations not to call (options in `spec/conformance/README.md`).

The complete sample is `examples/echo`: unary operations, an operation that crashes on purpose, both subscription modes, a health item, a configuration section and host callbacks; `tests/Plugin/ConformanceTest.php` puts it in a temporary directory, generates the launcher and runs every case of the black-box runner.

## Behavior Shared with the Host

- **Payload decoding** (RFC-0011 rule 2; for the PHP approach see [Language Mapping](#language-mapping)): the payload first passes the shared JSON text check and is then checked against the shape in text order; the first problem returns `KERNEL_VALIDATION_001` + `kernel.operation.invalid_payload` with arguments `id` and `reason`. `reason` holds only the JSON path of the error location: syntax errors, `null`, a non-object and a required member missing at the root write `$`; duplicate members write the path of the first duplicate; a value of the wrong type writes its own path (such as `$.lines[1].quantity`; member names containing spaces, dots, quotes and similar characters are written as `$['unit price']`, and `JsonPath` builds paths the same way). An empty payload is equivalent to `{}`; whitespace alone is not JSON.
- **Typed invocation**: `invokeTyped` checks only two things before entering the pipeline, in this order: an unregistered operation returns `KERNEL_NOTFOUND_001`, and a type that does not match the registration returns `KERNEL_VALIDATION_002` + `kernel.operation.type_mismatch`, with `id` as the only argument.
- **Built-in steps**: the invoker carries three built-in steps, placed where the .NET built-in middleware sits (RFC-0011 rule 10): all at the `Beginning` of their stage under the owner `xihan.kernel.core`, ordered with other middleware at the same position per RFC-0004 (ordinal order of owners, with `app` before it).
  - `ObserveMiddleware` in the Observe stage translates exceptions thrown by middleware and handlers after it into `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`, with the error of a framework exception carried in `inner` (rule 5); exceptions thrown by those before it (the Ingress stage, or middleware at the `Beginning` of the Observe stage whose owner sorts before `xihan.kernel.core`) propagate to the caller unchanged. To record the original exception, put your own middleware at the `End` of the Observe stage to catch it and rethrow.
  - `DeadlineMiddleware` in the Resilience stage checks the deadline against the context's clock on entry; if it has passed, it returns `KERNEL_TIMEOUT_001` + `kernel.invocation.deadline_before_start`, and later middleware and the handler do not run. It does not check cancellation on entry, and constructing the context does not make this check either. Cancellation along the way is attributed per RFC-0003 rule 1: when downstream throws amphp's `Amp\CancelledException` (the SDK does not depend on amphp and recognizes it by class name; the Observe step does not treat it as an unhandled exception), or writes cancellation as a `KERNEL_CANCELLED_001` result, a passed deadline gives `KERNEL_TIMEOUT_001` + `kernel.invocation.deadline_exceeded`, and otherwise a fired caller token gives `KERNEL_CANCELLED_001` + `kernel.invocation.cancelled`; a cancellation exception with neither fired propagates to the caller unchanged, as in .NET.
  - `ValidationMiddleware` in the Validate stage decodes the payload in raw invocations (available afterwards from `Current::requestObject()`) and returns `KERNEL_VALIDATION_001` on failure; typed invocations skip it.
  - The `PipelineBuilder` passed in is left unchanged, and the built-in steps are registered on a copy of it; registering middleware with the same name again is a duplicate registration.
- **Response encoding**: when the handler succeeds, the response object is written to the item bag (`Current::responseObject()`), and the XGI entry point encodes it into the payload only after the pipeline finishes, so middleware sees the result before encoding (RFC-0011 rule 10 "Encoding"). When it cannot be written (a float that is NaN or infinite, invalid UTF-8, a throwing encoder, an unsupported value), the result is `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`, with the error of a framework exception carried in `inner`; nothing is thrown to the caller and there is no payload. A typed NaN is not written as `null` or a string.
- **No response**: when the pipeline ends successfully without a response (middleware short-circuits with success, the handler does not run, and no recorded response is handed over through `Current::setResponsePayload`), both entry points return `KERNEL_UNEXPECTED_001` + `kernel.operation.no_response` (RFC-0011 rule 9).
- **Cancellation and deadlines**: signaled only through the token, and the invoker does not forcibly abort middleware or handlers: if the handler returns normally after the token fires, that result is the result of the invocation (RFC-0003 rule 1).
- **Baggage and `traceparent`**: values of registered baggage keys must be non-empty, at most 256 UTF-16 code units, and free of U+0000–U+001F and U+007F–U+009F (conventions/baggage-keys.md): `Context::create(baggage: …)` takes external input and drops nonconforming members; `withBaggage()` derives entries one by one inside the program and throws `InvalidArgumentException` for a nonconforming value; `xihan.idempotency-key` is exempt in both cases. `traceparent` accepts only version `00` and lowercase hex; an invalid one is treated as absent and a new trace is started. Sampling looks only at the lowest bit of the flags, only the sampled bit is written (`00` / `01`), and `01` is written when there is no upstream.
- **Kernel errors**: codes, keys, arguments and en-US templates match the spec's shared table (`kernel-messages.json`) verbatim, and `KernelMessages` carries these English templates (plus `kernel.manifest.*` and `primitives.manifest.*` for manifest reading, taken from the .NET en-US language file): they are used when the catalog cannot resolve a kernel key, and the messages of configuration-time exceptions are written in English with them. Duplicate registrations and a full registry carry keys and arguments from the shared table (`id` and `owner` for `kernel.operation.duplicate`, `capacity` for `kernel.operation.registry_full`).
- **Templates**: formatted per RFC-0010 "Templates".
  - Values are first mapped to the value model (see [Language Mapping](#language-mapping) for PHP); arrays and objects are written as compact JSON, object members are sorted by the UTF-16 code units of their names, and containers nested deeper than 64 levels are written as `null`.
  - Format specifiers must match `^[DdFfNnXx][0-9]{0,2}$`: `D` and `X` / `x` apply only to integers (`X` only to non-negative integers), and `F` and `N` apply to integers and floats, rounding the exact value of the float with ties to even (`{n:F2}` gives `0.12` for 0.125 and `2.67` for 2.675); any other specifier (`E2`, `G`, `0.00`, `yyyy`, printf style, `D100`) and any value a specifier does not apply to is output unformatted.
  - A `null` value is written as an empty string; floats between 1e-4 and 1e17 are written in the shortest round-trip fixed-point form, and outside that range as exponents such as `1E+17` and `9.9E-05`; negative zero is written as `-0`, and NaN and infinities as `NaN`, `Infinity` and `-Infinity`.
  - `MessageTemplate::format()` / `tryFormat()` and `MessageCatalog` take the decimal and group separators by locale (`MessageTemplate::numberSymbols()`): de-DE, es-ES and pt-BR use `,` and `.`, fr-FR uses `,` and U+202F, ru-RU uses `,` and U+00A0, and every other locale, or no locale, uses `.` and `,`. The decimal separator applies to unformatted floats and to `F` and `N`, the group separator applies only to `N`, unformatted integers are not grouped, and `D`, `X` and numbers inside arrays and objects are not affected by the locale.
  - `describe` uses the invariant culture, with arguments in ordinal order of their names; message keys are at most 128 characters long.
- **Manifest reading**: follows the order of RFC-0002 parsing rule 2 and reports only the first problem. Every failure throws `ConfigurationException`, `toError()` is the verbatim error, the code is always `KERNEL_CAPABILITY_006`, and `message()` and the exception message are sentences formatted from the English templates of these keys in the shared table (`kernel-messages.json`):
  1. Shared JSON text check: non-JSON gives `kernel.manifest.invalid_json`, with `reason` `$`, or the path of the first duplicate when any level has duplicate members. `read()` checks the text as is, so a leading BOM is a syntax error; `readFile()` skips a leading UTF-8 BOM, and a missing file gives `kernel.manifest.file_missing` (argument `path`).
  2. The root is `null`: `kernel.manifest.empty`, with no arguments.
  3. Schema check, item by item: `kernel.manifest.invalid`, with `reason` the path of the first problem. Members are checked in text order; for each member, members outside the Schema, `null`, the type and the value are checked in turn, descending into objects and arrays; after an object's members are checked, missing members are reported in the order of `required`. Interface versions have no leading zeros and do not exceed 2147483647, and only versions in `requires` may carry a single `^`.
  4. Cross-field constraints (`Manifest::validate()`, not checked when a manifest is constructed): in the order `isolation_required`, `isolation_not_allowed`, `duplicate_provides`, `duplicate_requires`, `duplicate_bindings`, with keys `primitives.manifest.*` and `id` as the only argument. The rule that only Wasm plugins can contribute middleware is checked by the host when it discovers plugins, not when reading.
- **Manifest writing**: the layout of `toJson()` is fixed: two-space indentation, LF line breaks only, no trailing newline, `": "`, empty arrays as `[]`; members in a fixed order, optional members without a value omitted, lists always written, `$schema` written as `https://spec.xihanfun.com/manifest/v1.json`, `role` written as `provider` by default, `activation` written as `["onStartup"]` by default, and versions in `requires` written as numbers without `^`; strings escape only the characters that must be escaped.
- **Result and Error encoding**: the JSON encoding of `Result<T>`, `Error` and `Maybe<T>` follows RFC-0001 "Result" (ADR-0233) and matches the .NET reference implementation: success with a value is `{"ok":true,"value":…}`, success without a value writes only `{"ok":true}`, and failure is `{"ok":false,"error":{…}}`. Reading picks the entry point by the kind of result: the shared JSON text check comes first (duplicate members at any level are rejected, including inside `value`, `details` and `inner`), then the reader rejects a valueless result carrying `value` (`{}` and `null` count too), a failure carrying `value`, a success carrying `error`, optional members written as `null`, and an `Error` whose `message` is missing or empty; unknown members are ignored. The shared check runs only at JSON text entry points (the `fromJson` family); already-decoded values received by `fromWire` cannot reveal duplicates. Write with `toJson()`: numbers round-trip under the value model, 64-bit integers are exact, integral floats are written as `2.0`, `-0.0` and `1.0e+17`, and non-finite floats as the strings `NaN`, `Infinity` and `-Infinity`; when calling `json_encode` yourself, pass `JSON_PRESERVE_ZERO_FRACTION` and set `serialize_precision` to `-1`.
- **Out-of-process plugins** (RFC-0017, `spec/plugin/`; each item below follows `handshake.md`, `lifecycle.md` §7 and `invocation.md`):
  - Startup (`handshake.md` §1): before listening and writing the handshake line, the manifest and the declarations are checked: `kind` is `plugin`, `isolation` is `out-of-process`, there is no `contributes.pipeline`, `primitives` equals the primitives major version this SDK supports, `1`, every registered operation is in `contributes.operations`, and no (topic, type) pair of the subscriptions repeats; the topic grammar, unique operations and an `en-US` catalog are already checked when `Subscription`, `Registry` and `Catalog` are constructed, and health items are filtered by the manifest at run time. An invalid manifest, a missing `XIHAN_PLUGIN_SESSION` or `XIHAN_PLUGIN_PROTOCOL_VERSIONS`, and a failure to listen also refuse the start. A refused start does not listen and writes no handshake line; it writes one `error` log line to stderr and `serve()` returns `Runtime::EXIT_REFUSED` (1), so the host sees the process exit before the handshake. After listening, it writes one line `xihan-plugin/1 <network> <address>` to stdout and writes nothing more to stdout.
  - Endpoint (§2, §4): on Linux and macOS a Unix domain socket inside a private directory created by this process (`0700`, a random name, and another name when it already exists), with the socket at `0600`, removed after stopping; on Windows loopback TCP (a random port on `127.0.0.1`), which other users on the machine can reach, so isolation rests on the session token alone. Addresses this SDK generates contain none of the whitespace of the spec (the set of §2, the same as `\s` in .NET regular expressions); when the temporary directory contains whitespace, is not valid UTF-8 or is too long, `/tmp` is used instead. `network` and `address` in `Options` can change this: `tcp` accepts only dotted decimal in `127.0.0.0/8` (without leading zeros) or `[::1]`, with a port from 1 to 65535, and `npipe` is not supported. PHP cannot serve named pipes without blocking, so this SDK never listens on one and named-pipe access control does not apply. `Endpoint` parses handshake lines and endpoints with the same whitespace set and tcp grammar.
  - Callback endpoint (§4): `XIHAN_PLUGIN_HOST_ADDRESS` is a list ordered by the host's preference and separated by `;`, and the whole value is invalid when any entry is. At startup the plugin takes the first entry this SDK can connect to and keeps it: Unix domain sockets (outside Windows) and loopback TCP; PHP cannot connect to named pipes. The .NET host always puts a loopback TCP endpoint last (on Windows a named pipe plus loopback TCP), so on Windows callbacks go over loopback TCP. When the variable is missing, invalid or has no usable entry, the plugin serves as usual, writes one `warning` to stderr at startup, and every callback fails with `PLUGINS_UNAVAILABLE_001` + `plugins.host.unavailable` (`reason` `no supported callback endpoint`) without sending a request; `Host::endpoint()` is then `null`.
  - Session token (§4): every RPC (`Handshake` included) first checks the metadata `xihan-plugin-session` in constant time (`hash_equals`), and it must carry exactly one value: none, a mismatch, or two or more values (even when one of them is right) are rejected with `Unauthenticated` and nothing runs; the token is checked before the call order and before a streaming call reads its first frame.
  - Handshake (§3): picks the highest common version in the host's list (this SDK supports `1`) and rejects with `FailedPrecondition` when there is none; `primitives` is the manifest's value and `manifest` is the manifest text with a leading UTF-8 BOM removed; operation declarations come from the `Registry` and are unary only (`streaming: false`, in byte order of IDs), with contracts and JSON Schemas; subscriptions are written in declaration order, with `mode` always `competing` or `broadcast`; `catalogs` holds only the plugin's own catalogs (locales sorted by name), since the host provides the runtime's message keys and they are not sent with the handshake.
  - Call order (`lifecycle.md` §7.1): `Handshake` is accepted only in `Declared` (then `Resolved`), `Configure` only in `Resolved` (then `Configured`, or `Failed` on failure), `Start` only in `Configured`, and `Stop` in any state except `Declared`, `Draining` and `Stopped`; `Health`, `WatchHealth`, `Invoke`, `InvokeStream` and `HandleEvent` are accepted in any state. Any other combination is rejected with `FailedPrecondition`, does nothing and leaves the state unchanged.
  - Configuration (§7.2): an empty `configuration` equals `{}`; when it does not pass the shared JSON text check or is not an object, the configure hook is not called, the result is `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` `configure`, `reason` `the configuration is not a JSON object`) and the plugin enters `Failed`. `Configuration` carries the section as is and adds typed reading (`value()`, `string()`, `int()`, `float()`, `bool()`): keys are split at `:`, array segments are indexes, and member names match ASCII case-insensitively; string leaves read as numbers follow the JSON number grammar (integers without fraction or exponent and within 64 bits), and read as booleans accept only `true` and `false` (ASCII case-insensitive); a missing value is `null`, and an unreadable one throws `InvalidArgumentException`. Callback permission checks use `granted_permissions`.
  - Start and readiness (§7.3): after the start hook succeeds the plugin enters `Started`; with a health hook it asks it once and enters `Ready`, `Degraded` or `Failed` by the result, and without one it enters `Ready`; only then does it answer. Only `Ready` and `Degraded` serve: calls and deliveries in any other state fail with `PLUGINS_UNAVAILABLE_001` + `plugins.process.unavailable` (`state` is the name of the current state, such as `Configured`, `Draining` or `Failed`).
  - Health (§7.4): before `Start` it reports the local state (`Declared`, `Resolved`, `Configured`) without health items and without calling the health hook; while serving, every `Health` asks the health hook once, only the `Ready`, `Degraded` and `Failed` it reports change the state (by the table of legal transitions, so `Failed` never comes back), health items outside `contributes.health` are dropped with one `warning` per name per process, and a throwing health hook makes this result `Degraded` with `error` `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` `health`) and no health items. `WatchHealth` pushes the current state first, then pushes whenever the state, health items or `error` change, asks the health hook again every 10 seconds while serving, pushes once on entering `Draining`, and ends the stream after answering `Stop`.
  - Stop (§7.5): when the start hook never succeeded, the stop hook is not called and the plugin answers `ok` and exits with code 0; `Started`, `Ready` and `Degraded` enter `Draining`, reject new calls and deliveries with `PLUGINS_UNAVAILABLE_001`, wait for in-flight calls up to the grace period (5 seconds when `grace_seconds` is 0), then signal their cancellation and stop waiting, call the stop hook (with the reason as is and the remaining grace in seconds), answer and exit with 0; a plugin that entered `Failed` after a successful start calls the stop hook the same way without changing state. The stop hook is called at most once per process; its failure or exception goes into `StopResponse.status`, and the plugin exits as usual.
  - Hook exceptions (§7.6): when the configure, start, stop or health hook throws, the exception text goes only to the stderr log and the host receives the simple class name as `reason` (no namespace; an anonymous class is written as `Parent@anonymous`, without the file path PHP appends to its name); a hook returning something other than a `Result` (a health hook, other than a `Health`) is treated as throwing `TypeError`.
  - Shutdown (§7.7): reaching the end of stdin and SIGTERM are both shutdown requests: a serving plugin enters `Draining`, signals the cancellation of every in-flight call at once and waits for them, and a plugin whose start hook succeeded calls the stop hook once if it has not been called (reason `shutdown`); at most 3 seconds after the request it exits with 0 whether or not this has finished, and a `Stop` in progress is bound by the same 3 seconds. SIGTERM needs the pcntl extension (Revolt dispatches signals with it, and it exists only on Unix): without pcntl, SIGTERM terminates the process by the system default; Windows has no SIGTERM, and the host closes stdin as the termination signal.
  - Invocation and context (`invocation.md` §1, §2): `Invoke` checks, in order, the session token, that the operation is declared in the handshake (otherwise `Unimplemented`), and that the plugin serves (otherwise `PLUGINS_UNAVAILABLE_001`), then restores the context from `InvocationMetadata` and runs through the SDK's invoker and the full pipeline, with an empty `payload` equal to `{}`. Restoring the context: `trace_parent` follows the RFC-0003 grammar, and an invalid one means no parent span and a new trace; `trace_state` does not enter the context; `baggage` keeps only registered keys (`xihan.principal` is handed to the author as is); `deadline` is read with the strict grammar (year 0001 to 9999, Gregorian dates, no leap second, within range after conversion to UTC; PHP instants have microsecond precision, so finer fractions are truncated), an unreadable one counts as absent, and the effective deadline is the earlier of it and the gRPC deadline. The host resetting the stream fires the cancellation token, and the token fires on time at the deadline. Recoverable failures go into `Status.error`, and gRPC statuses only signal protocol-level failures.
  - Streaming (§1): until RFC-0011 defines the streaming operation contract, plugins neither implement streaming calls nor declare streaming operations, and this SDK has no public API for them: `InvokeStream` reads the first frame; when the stream ends before it or it is not `start`, the stream ends with `InvalidArgument`, and when it is `start`, with `Unimplemented`, whether or not the operation is declared and the plugin is ready.
  - Writing and reading errors (§3): an error with a message key leaves `text` empty, and the host translates it into the caller's language from its catalogs; only free-text errors write `text`; `details` is the JSON object text of the arguments and details, empty when there are none; `inner` is written as well. Reading an `Error` from the host: when `code` does not match its grammar, the whole error is replaced by `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` `invoke`, `reason` `invalid error code '<code>'`); a `message_key` matching its grammar is used as the key (`text` is not taken), otherwise the error is free text with the text from `text`, or `code` when `text` is empty; `details` that is empty, fails the shared check or is not an object counts as absent, and `inner` follows the same rules; `ok` false without an `error` gives `reason` `the host reported a failure without an error`.
  - Delivery (§4): checks, in order, the session token; a missing `envelope`, or a `mode` other than empty, `competing` or `broadcast`, is rejected with `InvalidArgument`; subscriptions are found by (topic, mode, type), and when none matches the result is `KERNEL_NOTFOUND_001` + `plugins.event.unsubscribed` (`id`, `topic`, `type` and `mode`, with an empty mode written as `competing`), and the message is not handed to a subscription of the other mode; when the plugin does not serve, `PLUGINS_UNAVAILABLE_001`; then the context is restored and the matching subscriptions get the message one by one in declaration order, the first failure being the result; a throwing handler gives `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`.
  - Callbacks (§5): before sending, `Host::invoke` and `Host::publish` check locally, in order, and send nothing on a failed check: that a callback endpoint is usable (see "Callback endpoint"); the permission (`capability:kernel.pipeline` for Invoke, `capability:messaging.queue` for Publish, which must be both in the manifest's `permissions` and among the permissions granted by `Configure`, otherwise `PLUGINS_DENIED_002` + `plugins.callback.denied`); and that `xihan.tenant` of the callback context is the tenant of a call or delivery the plugin is handling at that moment (otherwise `PLUGINS_DENIED_002` + `plugins.callback.tenant_denied`). For `publish` each of these is a result for the whole batch; the `xihantenant` extension of an envelope is not checked locally, and the host judges it item by item. Callbacks carry the session token, and their `metadata` comes from the invocation context they run in: the traceparent, `deadline` written in UTC with seven fractional digits and `+00:00`, the registered baggage and an empty `trace_state`, with the gRPC deadline equal to `deadline`; the caller's cancellation cancels the callback. gRPC statuses map per the table of §5: `Unauthenticated` is `plugins.callback.session_invalid`, `PermissionDenied` is `plugins.callback.denied`, `DeadlineExceeded` is `KERNEL_TIMEOUT_001`, `Cancelled` with the callback context cancelled is `KERNEL_CANCELLED_001`, while `Cancelled` without it, `Unavailable` and connection failures are `PLUGINS_UNAVAILABLE_001` + `plugins.host.unavailable` (`reason` `<status name>: <description>`); `Unimplemented` and `InvalidArgument` of `Host.Invoke` are `kernel.operation.unknown` and `kernel.operation.invalid_payload`, and anything else (including those two for `Host.Publish`) is `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` the operation ID or `publish`). `publish` sends nothing for an empty list; when the RPC fails every item has the same error, and when the number of results differs from the number of envelopes every item is `plugins.process.failed` (`reason` `the host returned <n> results for <m> envelopes`).
  - Logging: written to stderr, one JSON object per line: `level` (`trace` / `debug` / `information` / `warning` / `error` / `critical`), `message`, and the remaining members as scope properties (`plugin`, `instance` and so on); plugins can use `Logger` themselves.
  - Message keys (§8): error codes, message keys and arguments of the runtime follow the spec's `plugin-messages.json`: `plugins.process.unavailable`, `plugins.process.failed`, `plugins.event.unsubscribed`, `plugins.host.unavailable`, `plugins.callback.denied`, `plugins.callback.tenant_denied` and `plugins.callback.session_invalid`; the arguments are the error's `details`, `id` is always the manifest ID, and `reason` is English text that is not localized. The templates of the 10 locales are in `src/Plugin/Localization` (`PluginMessages::catalog()`, for local rendering), with built-in en-US templates as well; the host has its own catalog of these keys, so the handshake does not send them.

The lifecycle transition table, pipeline stage order, error codes, baggage keys and values, capability requirement text, the JSON text check, wire encoding, message templates, and the plugin handshake lines, protocol version negotiation, callback endpoint lists, deadlines, callback failure mapping and runtime message keys are verified by `spec/conformance/vectors`, and the behavior of the plugin protocol by the black-box runner of the spec repository.

## Language Mapping

The spec leaves language-dependent details for each SDK to document (ADR-0236). The PHP approach:

- **Shared JSON text check** (RFC-0001 "JSON Text"): syntax, nesting depth, lone surrogate escapes and raw control characters are left to `json_decode`; invalid UTF-8 (including overlong encodings and surrogates encoded as UTF-8) is rejected by PCRE's UTF-8 validation; duplicate members are found in the original text (`json_decode` keeps the last of duplicates). Once past the check, payloads and manifests are read by an internal reader into a tree that keeps text order and the original spelling, without going through `stdClass`, so member names starting with U+0000 are checked and reported with paths as usual. Wire encoding (`Result::fromJson`, `Error::fromJson`) and untyped payloads (`Codec::json()`) are read by the same reader under the value model, also without going through `stdClass`.
- **Grammar matching** (RFC-0001 "Grammar Matching"): PCRE's `$` also matches before a trailing newline, so every regex for a spec grammar carries the `D` modifier; `xihan.tenant\n`, a `traceparent` with a newline and `kernel.hosting@1\n` are all invalid.
- **Value model** (RFC-0010 "Templates"): `null`, `bool`, `string`, `int` (PHP's `int` is 64-bit) and `float` map as is; `json_decode` reads integer literals within the 64-bit range as `int` and everything else as `float`, consistent with the model. JSON objects read by the SDK are `JsonObject`: immutable, members in text order, member names kept as is (names starting with U+0000 and purely numeric names both work), `{}` and `[]` never confused; access members with `$object['name']` or `get()`, get a new object with one member changed from `with()`, and `toJson()` and response encoding write members as is; when you `json_encode` it yourself it becomes a `stdClass` (an associative array when a member name starts with U+0000). A PHP array is an array when it is a list (`array_is_list`, including the empty array `[]`), and otherwise an object with keys written as strings; `stdClass` is also an object. Values outside the model are written as PHP text: `BackedEnum` uses the text of its value, `UnitEnum` its name, `Stringable` `(string)`, `DateTimeInterface` the ATOM format (`2026-11-16T10:00:00+08:00`), `JsonSerializable` maps the result of `jsonSerialize()`, and any other object writes its type name. These do not cross languages; a plugin that needs cross-language formatting converts them to strings first.
- **Request shape** (RFC-0011 rule 2): members are declared with `Shape`; member names are case-sensitive, unknown members are ignored, and numbers are not read from strings.
  - Required: `Shape::string()->required()`; when missing, the path of the enclosing object is reported when that object ends; only presence is required, and a `null` value counts as present.
  - Optional: without `required()`; when missing, the key is absent from the array passed to the factory function.
  - Accepting `null`: `string()`, `listOf()`, `mapOf()`, `object()` and `any()` accept `null` (meaning no value); `int32()`, `int64()`, `float()`, `bool()` and their array items and map values do not, unless `nullable()` is added.
  - Integers reject `1.0` and `1e2`, and out-of-range values are mismatches; `float()` accepts integer literals, `1e400` is infinity and `1e-400` is 0.
  - Values passed to the factory function: objects and maps are arrays keyed by member name (PHP converts purely numeric keys to integers).
  - Arbitrary JSON: `any()` yields `RawJson`, whose `json` is the original text read and whose `decode()` gives the object-mode result of `json_decode`; responses and `toJson()` put the original text back as is, so `1e400`, integers beyond double precision and `2.0` keep the same JSON value when written back (RFC-0011 rule 2). `RawJson::of()` wraps your own JSON text after it passes the shared check.
  - `Codec::json()` does not check shapes, and the request is a `JsonObject` read under the value model: integers within the 64-bit range are exact, and overflowing numbers such as `1e400` are read as double-precision infinity, as in .NET. Placed in untyped values such as error details they are written as the string `"Infinity"`; returned as is in a response they cannot be written (`unhandled_exception`). To keep the original text as is, use `typed()` with `any()`.

## Design

- **Failures**: recoverable failures return `Result::fail(...)` instead of throwing; programming errors and configuration errors throw exceptions carrying error codes (the `FrameworkException` interface): invalid arguments are `InvalidArgumentException`, assembly errors such as manifest files, pipeline constraints and duplicate operation registrations are `ConfigurationException`, and forcing a value out of a failed `Result` is `FailureException`.
- **Synchronous signatures and cancellation**: middleware and handler signatures are synchronous and can run inside a Fiber. The cancellation token can be polled and can register callbacks: `$context->cancellation()->isRequested()`, and `$context->cancellationError()` gives `KERNEL_TIMEOUT_001` or `KERNEL_CANCELLED_001`; without an event loop, the deadline is checked against the clock when polled, and with an event loop the host calls `DeadlineCancellation::poll()` at the deadline.
- **Generics**: annotated with PHPStan's `@template`.
- **Plugin runtime**: runs on the amphp event loop (Revolt) with one Fiber per call; handlers keep synchronous signatures, so a blocking handler holds up the other calls in the same process, and slow I/O should use amphp's non-blocking APIs. PHP's gRPC extension only provides a client, so this SDK implements both the gRPC server and client (cleartext HTTP/2 with prior knowledge, no upgrade): frame parsing and HPACK come from amphp/http, while connections, streams, flow control and gRPC messages, statuses and trailers are in `Plugin\Internal\Grpc`. Connections of the plugin protocol are local and long-lived (`WatchHealth` stays open), so there are no internet-facing limits such as idle timeouts or PING counts; memory is bounded by the receive window of each stream, the 4 MiB limit per message and 100 concurrent streams. Protocol messages use the pure PHP runtime of google/protobuf. No additional PHP extensions are needed: openssl, required by amphp/socket, and mbstring, required indirectly by amphp/http, are both in the official `php:8.3-cli` image.
- **Windows**: when PHP reads a non-blocking pipe that is open but empty it keeps waiting, and `stream_select` cannot tell whether a pipe is readable, so on Windows a PHP child process that only performs blocking reads of stdin is started and checked periodically for exit, and it is terminated when the plugin exits. PHP cannot connect to named pipes: on Windows the .NET host gives two callback endpoints, a named pipe and loopback TCP, and the plugin takes loopback TCP, so callbacks work as usual. Windows has no pcntl, so SIGTERM is not handled there, and the host closes stdin as the termination signal.

## Development

```bash
git submodule update --init   # spec/
composer install
composer check                # = composer lint (PSR-12), composer analyse (PHPStan at the highest level), composer test (PHPUnit)
```

Without PHP and Composer on the machine, use the official Docker images (PowerShell; in Git Bash, prefix the commands with `MSYS_NO_PATHCONV=1`):

```powershell
docker run --rm -v "${PWD}:/app" -w /app composer:2 install
docker run --rm -v "${PWD}:/app" -w /app php:8.3-cli vendor/bin/phpcs
docker run --rm -v "${PWD}:/app" -w /app php:8.3-cli vendor/bin/phpstan analyse --memory-limit=1G
docker run --rm -v "${PWD}:/app" -w /app php:8.3-cli vendor/bin/phpunit
```

Then run them again with the image changed to `php:8.4-cli`. `composer.json` pins the platform for dependency resolution to PHP 8.3.0, so the same `vendor/` runs on both 8.3 and 8.4. CI runs the same gates on ubuntu and windows with PHP 8.3 and 8.4.

- The conformance test of the plugin runtime (`tests/Plugin/ConformanceTest.php`) runs the spec's black-box runner from the submodule with `go run` and needs Go (at least the version in `spec/conformance/go.mod`); it is skipped when `go` is not on `PATH`. The official PHP images have no Go: to verify locally, install the linux build of Go in the PHP container and then run `vendor/bin/phpunit`. CI installs Go, so the test really runs.
- The process-level tests (`tests/Plugin/ProcessTest.php`) run `examples/echo` as a child process: the SIGTERM case needs pcntl and is skipped without it; the official PHP images have no pcntl, which `docker-php-ext-install pcntl` adds.
- The protocol code `src/Plugin/Protocol/V1` is generated from `spec/plugin/plugin.proto` by `php scripts/generate-plugin-protocol.php` and committed: it needs protoc on `PATH`, from the same release as the google/protobuf runtime (stated in the script; change both together). Regenerate after changing the protocol; CI regenerates and checks that the result matches what is committed.
